Archivo modificado: apps/api/src/services/admin-registry.ts

Cambios:
  • AdminViewConfig extendida con groupBy, dateField, titleField, icon
  • Nueva función extractViewsFromManifest() — lee admin.views como fuente primaria
  • buildGrimoireAdminConfig() ahora usa extractViewsFromManifest() + fallback legacy
  • buildRealmGrimoireConfig() ahora usa extractViewsFromManifest() + fallback legacy
  • Normalización de tipos inválidos: "list" → "grid", "dashboard" → "custom"
  • hasCustomView ahora es inteligente: true solo si hay vistas type:"custom"
    declaradas, o si estamos en fallback legacy y detectamos archivo .svelte
  • defaultView respeta grimoire.json admin.defaultView
  • detectCustomView() simplificada drásticamente — usa getViewPath() para evitar
    falsos positivos de archivos compartidos (PostsView.svelte, Media.svelte, etc.)

Impacto:
  • Backend ya no fuerza monolitos para grimoires que declaran admin.views
  • Grimoires sin admin.views siguen funcionando con fallback legacy
  • Esports ya no reporta hasCustomView:true incorrectamente

┌─────────────────────────────────────────────────────────────────────────────┐
│  DECISIONES TOMADAS                                                         │
└─────────────────────────────────────────────────────────────────────────────┘

Filosofía aplicada: "Django Admin pero más dinámico"
  • CRM: Puro DataExplorer. Kanban básico con groupBy:"status" (suficiente
    para operar). NO dashboards, NO timelines (eso es producto).
  • Agile: Puro DataExplorer en grids. Board kanban eliminado del admin
    (es app de producto, debe ir al realm).
  • Conta: Hybrid. Grids para listados + custom forms para lógica de negocio
    (partida doble, reportes) que el DataExplorer no puede expresar.
