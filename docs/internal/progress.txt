FASE 1: CORE GENÉRICO — Desacoplamiento de Dominio Gaming
Fecha: 2026-04-19
Estado: COMPLETADO
═══════════════════════════════════════════════════════════════════

OBJETIVO
--------
Transformar el schema monolítico de Kitsuden en un core 100% dominio-
agnóstico, extrayendo las tablas gaming/blog/streamer a sus kons
correspondientes sin romper la compatibilidad con el CMS de gaming.

ARCHIVOS CREADOS
----------------
1. apps/api/src/db/schema-core.ts
   - Schema base con SOLO tablas de infraestructura:
     • Auth (authUsers, authSessions, authAccounts, authVerifications)
     • API Keys, Media, Data Sets, Data Entries, Site Settings
     • Formulas, Modules, Installed Kons
     • Actions, Action Executions
     • Agent System (identities, apiKeys, memory, auditLogs, traces, steps, feedback)
     • Data Sources
   - SIN tablas de dominio: games, platforms, tags, streamers, blogPosts,
     gameCollections, gameCollectionEntries, ni tablas de unión.
   - SIN FK gaming en dataSets (eliminada gameId).
   - Relaciones dataSets limpias (solo entries, sin game).

ARCHIVOS MODIFICADOS
--------------------
2. apps/api/src/db/schema.ts
   - Convertido en "Backward Compatibility Layer".
   - Re-exporta schema-core + tablas gaming desde kons vía imports
     nombrados (evita conflictos de enums duplicados).
   - Legacy imports como `import { games } from "../db/schema"` siguen
     funcionando durante la transición.

3. apps/api/src/lib/schema-merger.ts
   - Base de schema cambiada de `../db/schema` a `../db/schema-core`.
   - El runtime ahora construye el schema mergeado a partir del core
     genérico + kons activos.

4. apps/api/src/db/schema-all.ts
   - Revertido a exportar `./schema` (compat layer) para mantener
     compatibilidad con drizzle-kit push/migrate.
   - drizzle-kit sigue viendo todas las tablas (core + gaming).

5. apps/api/kitsuden.config.ts
   - Agregados kons gaming a BASE_FEATURE_KONS:
     • kon-games (enabled: true)
     • kon-streamers (enabled: true)
     • kon-esports (enabled: true)
   - Esto asegura que staticConfig los incluya y el schema-merger
     los cargue correctamente en runtime.

6. apps/api/src/routes/collections.ts
   - Imports de dominio gaming movidos de `../db/schema` a
     `../../../../packages/kons/kon-games/games.schema`.
   - Import core `media` permanece en `../db/schema`.

7. apps/api/src/routes/blog.ts
   - Imports de dominio movidos a sus kons respectivos:
     • blogPosts, blogPostsToTags, blogPostsToGames → kon-blog
     • tags, games → kon-games
   - Imports core `authUsers`, `media` permanecen en `../db/schema`.

8. apps/api/src/routes/datasets.ts
   - Eliminadas referencias a `gameId` en insert y update de dataSets.

9. apps/api/src/routes/crud.ts
   - Eliminada referencia a `gameId` en insert de dataSets.

10. apps/api/src/routes/datasets-openapi.ts
    - Eliminado `gameId` del schema Zod CreateDatasetPayloadSchema.

11. packages/shared/src/schemas.ts
    - Eliminado `gameId` de CreateDatasetPayloadSchema y
      UpdateDatasetPayloadSchema.
    - Paquete recompilado con `pnpm exec tsc`.

VERIFICACIÓN
------------
• TypeScript check (tsc --noEmit) ejecutado en apps/api.
• Ningún error nuevo detectado en los archivos modificados.
• Errores pre-existentes en agents-v1.ts, openapi-aggregator.ts y
  docs-dynamic.ts NO fueron introducidos por esta fase.
• El CMS de gaming sigue funcionando mediante dogfooding:
  schema.ts (compat) re-exporta las tablas de los kons.

NOTAS TÉCNICAS
--------------
- La eliminación de la columna `gameId` de `data_sets` requiere una
  migración de base de datos cuando se decida aplicar el schema real.
  Por ahora, drizzle-kit sigue viendo la columna vía schema.ts compat.
- Los enums `contentStatusEnum` existen tanto en core como en kon-games.
  El schema-merger sobrescribe el del core con el del kon (misma
  definición), sin generar conflictos en runtime.

FASE 2: RUNTIME EXTENSIBLE — Kons desde NPM
Fecha: 2026-04-19
Estado: COMPLETADO
═══════════════════════════════════════════════════════════════════

OBJETIVO
--------
Permitir que Kitsuden se extienda sin modificar el monorepo:
instalar kons desde npm, resolver dependencias automáticamente,
y registrarlos en la base de datos.

ARCHIVOS CREADOS
----------------
1. packages/cli/src/commands/install.ts
   - Comando `kitsuden install <kon>` implementado:
     • Detecta package manager (pnpm/npm/yarn)
     • Ejecuta instalación del paquete
     • Lee kon.json / package.json con campo kitsuden
     • Instala dependencias de kons recursivamente
     • Ejecuta migraciones SQL desde <pkg>/migrations/
     • Registra en tabla installed_kons de PostgreSQL
     • Muestra instrucciones de reinicio

2. packages/cli/templates/kon-npm-package/
   - Template estándar de paquete npm para kons:
     • package.json (con campo kitsuden.type = "kon")
     • kon.json (manifest completo)
     • index.ts (entry point + KonDefinition)
     • schema.ts (Drizzle ORM schema)
     • routes.ts (Hono router factory)
     • migrations/0000_initial.sql (DDL idempotente)
     • README.md (documentación completa)

ARCHIVOS MODIFICADOS
--------------------
3. apps/api/src/lib/module-loader.ts
   - Agregada función sortKonsByDependencies():
     • Ordenamiento topológico de kons por dependencies.kons
     • Detecta ciclos y lanza error descriptivo
   - Loop de carga ahora usa sortedKons en lugar de resolvedKons
   - Kons con dependencias se cargan DESPUÉS de sus dependencias

4. apps/api/src/lib/schema-merger.ts
   - Agregada búsqueda de schemas en node_modules:
     • @kitsuden/kon-xxx
     • kon-xxx (community)
     • Scoped packages (@scope/kon-xxx)
   - Schema-merger ahora puede cargar tablas de kons instalados
     vía npm, no solo desde packages/kons/ local.

5. packages/cli/src/index.ts
   - Registrado nuevo comando:
     kitsuden install <kon> [--dev]

VERIFICACIÓN
------------
• CLI compila sin errores (tsc --noEmit en packages/cli).
• module-loader.ts y schema-merger.ts compilan sin errores.
• Ningún error nuevo en apps/api tras los cambios.

PRÓXIMAS FASES
--------------
Fase 3: API Unificada (/api/items/{collection})
Fase 4: Admin 100% Dinámico
Fase 5: Multi-Tenancy (opcional)

NOTAS TÉCNICAS
--------------
- El comando install requiere DATABASE_URL para registrar en
  installed_kons. Si no está disponible, instala el paquete pero
  omite el registro en DB.
- Las migraciones se ejecutan vía postgres.js en orden alfabético.
  Se recomienda usar IF NOT EXISTS para idempotencia.
- El schema-merger carga schemas .ts directamente desde node_modules.
  En producción bundleado, los kons deben compilar su schema a .js
  o usar el fallback de migraciones SQL.
- El orden topológico en module-loader usa el campo dependencies.kons
  del manifest. También soporta el formato legacy dependencies: string[].

FASE 3: API AUTO-GENERADA — REST Unificado + OpenAPI + GraphQL + SDK
Fecha: 2026-04-19
Estado: COMPLETADO
═══════════════════════════════════════════════════════════════════

OBJETIVO
--------
Cualquier dataset o kon expone REST + GraphQL automáticamente,
con OpenAPI spec dinámica y SDK auto-generado para el frontend.

ARCHIVOS CREADOS
----------------
1. apps/api/src/routes/items.ts
   - Router unificado `/api/items/{collection}` que funciona para:
     • Datasets (JSONB en data_entries)
     • Tablas nativas de kons (PostgreSQL)
   - Endpoints estándar REST:
     GET    /api/items/:collection         → listar con filtros
     GET    /api/items/:collection/:id     → obtener uno
     POST   /api/items/:collection         → crear
     PATCH  /api/items/:collection/:id     → actualizar
     DELETE /api/items/:collection/:id     → eliminar
   - Query params: limit, offset, sort, where (JSON)
   - Soporte de auth opcional (reads públicos, mutations protegidas)
   - Broadcast de mutaciones vía realtime

2. packages/cli/src/commands/generate-sdk.ts
   - Comando `kitsuden generate-sdk`:
     • Consume `/api/docs/openapi.json` en runtime
     • Genera hooks React/TypeScript listos para usar
     • Hook genérico `useVekItems(collection)` con CRUD completo
     • Hooks específicos por operación desde la spec

ARCHIVOS MODIFICADOS
--------------------
3. apps/api/src/index.ts
   - Montado router itemsRoutes en `/api/items`
   - Log de inicialización incluye "Unified Items API"

4. apps/api/src/db/index.ts
   - Exportado `mergedSchema` para acceso runtime desde routers
   - Permite a `items.ts` y `graphql.ts` descubrir tablas dinámicamente

5. apps/api/src/lib/openapi-aggregator.ts
   - Agregados paths estáticos de "Unified Items" a la spec:
     • /items/{collection} (GET, POST)
     • /items/{collection}/{id} (GET, PATCH, DELETE)
   - Tag "Unified Items" documentado en OpenAPI
   - La spec ahora incluye tanto kons como endpoints unificados

6. apps/api/src/routes/graphql.ts
   - Agregado campo dinámico `items(collection, id, page, limit, where)`
     • Funciona para datasets y tablas nativas
     • Devuelve JSON flexible (GraphQLJSON)
   - Agregado campo `collections` que lista:
     • datasets registrados
     • tablas nativas disponibles en mergedSchema
   - GraphQL ahora es un wrapper dinámico sobre el REST unificado

7. packages/cli/src/index.ts
   - Registrado nuevo comando:
     kitsuden generate-sdk [--lang typescript] [--output dir] [--base-url url]

VERIFICACIÓN
------------
• TypeScript check sin errores nuevos en apps/api ni packages/cli.
• items.ts, graphql.ts, db/index.ts, openapi-aggregator.ts compilan.
• generate-sdk.ts compila correctamente.

NOTAS TÉCNICAS
--------------
- El endpoint /api/items/{collection} detecta automáticamente si la
  colección es un dataset (buscando en data_sets.slug) o una tabla nativa
  (buscando en mergedSchema). Usa SQL raw para tablas nativas cuando
  Drizzle no puede resolver la tabla dinámicamente.
- GraphQL usa GraphQLJSON para devolver estructuras flexibles. En una
  versión futura se pueden generar tipos GraphQL estáticos a partir del
  schema del dataset o de la tabla.
- generate-sdk requiere que la API esté corriendo para leer la spec.
  En modo CI/CD, la spec puede cachearse previamente.
- Los hooks generados usan fetch nativo con credentials: 'include' para
  soportar cookies de sesión (Better-Auth).

FASE D — DEUDA TÉCNICA CORREGIDA
Fecha: 2026-04-22
Estado: COMPLETADO
═══════════════════════════════════════════════════════════════════

OBJETIVO
--------
Corregir los 3 gaps de deuda técnica identificados en la revisión de Fase D:
1. RLS inexistente en items.ts
2. GraphQL con tipos hardcodeados de gaming
3. getNativeTable con heurística simple (solo ±s)

ARCHIVOS MODIFICADOS
--------------------
1. apps/api/src/routes/items.ts (REFACTOR MAYOR)
   - Renombrado import `db` → `rawDb`
   - Agregado helper `getDb(c)` que devuelve `c.get("tx") || rawDb`
   - Agregado middleware `withTransactionalRLS()` en TODAS las rutas:
     • Reads: transacción RLS (políticas aplicadas consistentemente)
     • Mutations: requireAuth + transacción RLS
   - Refactorizadas todas las funciones helper para recibir `db` como parámetro:
     • findDatasetBySlug(db, slug)
     • resolveCollection(db, collection)
   - Mejorado `getNativeTable()` con resolución robusta de plural/singular:
     • Mapa de plurales irregulares (children→child, people→person, etc.)
     • Soporte para terminaciones -ies, -es, -ches, -shes, -xes, -zes
     • Búsqueda case-insensitive en todas las claves de mergedSchema
     • Set de candidates para evitar duplicados

2. apps/api/src/routes/graphql.ts (REFACTOR MAYOR)
   - queryFields reestructurado: campos universales primero, legacy condicional
   - Campos universales (siempre disponibles):
     • items(collection, id, page, limit, where)
     • collections
     • media
     • dataEntries
   - Campos legacy cargados condicionalmente desde mergedSchema:
     • blogPost / blogPosts  → solo si existe mergedSchema.blogPosts
     • game / games          → solo si existe mergedSchema.games
     • tags                  → solo si existe mergedSchema.tags
     • platforms             → solo si existe mergedSchema.platforms
     • streamers             → solo si existe mergedSchema.streamers
   - Si Kitsuden corre sin kons gaming, el schema GraphQL es 100% genérico.

VERIFICACIÓN
------------
• items.ts compila sin errores nuevos.
• graphql.ts compila sin errores nuevos.
• Handlers de items.ts usan transacción RLS (c.get("tx")) en lugar de db raw.
• GraphQL schema se adapta dinámicamente a los kons activos.

NOTAS TÉCNICAS
--------------
- `withTransactionalRLS()` envuelve cada petición en transacción PostgreSQL
  e inyecta app.current_user_id. Las queries dentro del handler usan la
  misma transacción (c.get("tx")), garantizando que RLS se aplique.
- Para lecturas públicas, el middleware RLS igual se aplica para consistencia.
  Si una tabla no tiene políticas RLS, PostgreSQL ignora el contexto sin
  penalidad de performance significativa.
- GraphQL tipos estáticos (BlogPostType, GameType, etc.) siguen definidos en
  el archivo por requerimiento de graphql-js, pero sus campos en QueryRoot
  solo se registran si la tabla existe. Esto evita errores de resolución.

NOTAS TÉCNICAS
--------------
- KonPage.svelte soporta dos modos:
  1. LEGACY: carga vista custom monolítica desde KON_VIEW_REGISTRY
  2. HYBRID: renderiza tabs con DataExplorer (grid/kanban/calendar) +
     vistas custom type="custom" declaradas en kon.json
- El kon-loader.ts hace auto-detección de vistas por convención:
  /src/views/{kon}/{PascalCase}View.svelte
- Si un kon no tiene vista custom, usa DataExplorer con config
  auto-generada desde /api/admin/registry.
