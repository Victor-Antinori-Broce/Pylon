# Models: declare once with `defineModelo`

A developer (or their AI) declares a model **once**. From that declaration
Kitsuden derives:

| What | Where it comes from |
| --- | --- |
| The Drizzle table | `tablaDeModelo(m)` (`@kitsuden/engine`) |
| The migration, and the `makemigrations` diff when the model changes | `kitsuden makemigrations` → `generarMigracionDeModelos` (`@kitsuden/shared`) |
| REST CRUD, OpenAPI 3.1 and MCP tools | six kon SDK operations (`defineOperacion`), generated by `operacionesDeModelo` |
| Validation (zod 4) and `422` problem+json | `esquemasDeModelo(m)`; unknown fields get a "did you mean" |
| RLS policies from the declared access policy | in the generated migration, with `FORCE ROW LEVEL SECURITY` |
| Agent scopes `<model>:read` / `<model>:write`, and approval sensitivity | `scopesDeModelo(m)`; DELETE is sensitive by default |
| The admin panel view (list, create, edit) | `descriptorDeModelo(m)` → `/models` in the panel |
| Idempotency and `KITSUDEN_E_*` errors | inherited from the host, like every SDK operation |

It fits the kon SDK instead of sitting beside it: a kon made of models is a
normal `defineKonSdk` kon, so the module loader, the per-request RLS
transaction, the OpenAPI document, the MCP server, the coverage test and the
authorization matrix treat it like any other.

## A model

```ts
// packages/kons/kon-notas/src/notas.modelo.ts
import { campo, defineModelo } from "@kitsuden/shared";

export const note = defineModelo({
  nombre: "note", // singular, kebab-case; it is part of the contract
  etiqueta: "Note",
  descripcion: "A personal note. Each account sees only its own.",
  campos: {
    title: campo.texto({ max: 200, requerido: true }),
    body: campo.textoLargo(),
    status: campo.enumerado(["draft", "published"], { requerido: true, porDefecto: "draft" }),
    priority: campo.entero({ min: 0, max: 5, requerido: true, porDefecto: 0 }),
    pinned: campo.booleano({ requerido: true, porDefecto: false }),
    dueAt: campo.fecha(),
    slug: campo.texto({ max: 80, unico: true }),
    meta: campo.json(),
  },
  acceso: { leer: "dueno", escribir: "dueno" }, // REQUIRED
});
```

And the kon:

```ts
// packages/kons/kon-notas/index.ts
import { defineKonDeModelos } from "@kitsuden/engine";
import { note } from "./src/notas.modelo";

export const kon = defineKonDeModelos({
  id: "kon-notas",
  name: "Notes",
  version: "0.1.0",
  mountPath: "/api/notas",
  modelos: [note],
  // operaciones: [...] — your own hand-written operations, mounted after the models'
});
```

A complete, tested example lives in `tests/unit/fixtures/kon-notas/` (a
personal-notes model and a public-read, staff-write categories model, with the
migration `kitsuden makemigrations` generated for them).

### Field types

| Builder | Postgres | Input (JSON) | Notes |
| --- | --- | --- | --- |
| `campo.texto({ min, max })` | `varchar(max)` or `text` | string | `requerido` implies at least 1 character |
| `campo.textoLargo({ max })` | `text` | string | not sortable, not shown in the panel list |
| `campo.entero({ min, max })` | `integer` + CHECK | integer | 32-bit range is enforced |
| `campo.numero({ min, max })` | `double precision` + CHECK | number | |
| `campo.booleano()` | `boolean` | boolean | filterable: `?pinned=true` |
| `campo.fecha({ porDefecto: "ahora" })` | `timestamptz` | ISO 8601 string | "ahora" is `now()` |
| `campo.enumerado([...])` | `text` + CHECK | one of the values | filterable; a CHECK, not a Postgres enum, so values can change |
| `campo.json()` | `jsonb` | object or array | |
| `campo.uuid()` | `uuid` | uuid | filterable |

Common options: `requerido`, `unico` (409 `KITSUDEN_E_CONFLICT` on repeat),
`porDefecto` (lives in the column `DEFAULT`, validated when you declare it),
`indice`, `etiqueta`, `descripcion`, and `antes` (the field's previous name: the
next migration renames the column instead of dropping it).

Every table also gets `id uuid` (primary key), `created_at`, `updated_at`
and, when an access rule mentions the owner, `owner_id text`. Those are set by
the server; a client cannot send them (`ownerId` in a create body is a 422).

## Access policy (required)

There is no model without `acceso`. `defineModelo` throws when it is missing,
unknown, or asks for public writes.

| `leer` | Who reads rows |
| --- | --- |
| `publico` | anyone, also without a session |
| `dueno` | each account its own rows (`owner_id`); an admin, or an agent that opens the whole kon, all of them |
| `staff` | admin and editor accounts, or an agent with `<model>:read` (or the whole kon) |

| `escribir` | Who creates, edits, deletes |
| --- | --- |
| `dueno` | any account creates; edits and deletes only its own rows (admins: all) |
| `staff` | admin and editor accounts, or an agent with `<model>:write` (or the whole kon) |

`leer: "dueno", escribir: "staff"` is "the team assigns rows that each owner
reads": the create body then accepts an optional `ownerId`.
`leer: "staff", escribir: "dueno"` is rejected (owners could not read what they
write). There is deliberately no "every signed-in account reads everything":
`verify-rls` reports rows a stranger sees and the anonymous user does not as a
leak.

The policy is enforced three times, each independent of the others:

1. **Operation permission**, before the body is read: the model scope, a fine
   or broad kon scope, `admin`, or the `<model>` policy for human accounts.
2. **Row filter** in the generated handlers (owner), mirroring the RLS.
3. **Postgres RLS** in the generated migration (`ENABLE` + `FORCE`, four
   policies per table), using the core functions
   `kitsuden_admin_efectivo(kon)`, `kitsuden_staff_efectivo(kon)` and
   `kitsuden_agente_puede_en_kon(kon, scope)` from
   `apps/api/src/db/funciones-de-agente.sql`. The system context (empty id and
   role: migrations, loaders, workers) sees everything, like every other table.

The test `tests/unit/modelos-kon-notas.test.ts` weakens the RLS policy on
purpose and checks that the probe notices (and that the handler filter still
isolates), then restores it with the same SQL the migration contains.

## Agents and scopes

| Scope | Opens |
| --- | --- |
| `<model>:read` | `describe-`, `list-`, `get-` (on `dueno` models: the agent's own rows) |
| `<model>:write` | `create-`, `update-`, `delete-` |
| `kon:<kon>:<operation>` | that one operation |
| `<kon>:*` / `admin` | the whole kon (and, on `dueno` models, every row) |
| `!<model>:write`, `!kon:<kon>:*`… | a deny wins over everything, `admin` included |

**Agents never write by default.** The human policy returns `false` for an
agent, so `usuario:actuar`, `mcp:read` or a read scope do not open writes; only
a write scope does. No agent preset includes a model scope.

Deletes are sensitive (`sensible.borrar`, default `true`): an agent in
approval mode gets `202 KITSUDEN_E_APPROVAL_REQUIRED` and a human decides. Set
`sensible: { crear: true }` or `{ actualizar: true }` to hold those too.

## The operations

For a model `note` (plural `notes`) mounted at `/api/notas`:

| Operation id | Route | MCP tool |
| --- | --- | --- |
| `describe-note` | `GET /api/notas/notes/_model` | `notas__describe-note` |
| `list-notes` | `GET /api/notas/notes?limit&offset&sort&<filter>` | `notas__list-notes` |
| `get-note` | `GET /api/notas/notes/:id` | `notas__get-note` |
| `create-note` | `POST /api/notas/notes` (201) | `notas__create-note` |
| `update-note` | `PATCH /api/notas/notes/:id` | `notas__update-note` |
| `delete-note` | `DELETE /api/notas/notes/:id` (204) | `notas__delete-note` |

The list returns `{ data, total, limit, offset }`; `limit` is 1–100 (default
20), `sort` is a field name with an optional `-` (default `-createdAt`),
and enum, boolean and uuid fields filter by equality. A row that does not exist
and a row you cannot see are the same 404.

`GET /api/models` (staff only, not an MCP tool) lists the descriptors of every
mounted model; the panel's **Models** page (`/models`) renders a list, a create
form and an edit form from each descriptor.

## Migrations: `kitsuden makemigrations`

```bash
kitsuden make model note --kon notas      # packages/kons/kon-notas/src/note.modelo.ts
kitsuden makemigrations                   # every kon with *.modelo.ts / modelos.ts
kitsuden makemigrations --kon notas -n add_color
kitsuden makemigrations --dir apps/api/src/modelos   # models outside a kon (kon name "app")
kitsuden makemigrations --dry-run         # print the SQL, write nothing
kitsuden makemigrations --allow-destructive
```

The command keeps `migrations/modelos.snapshot.json` next to the migrations: the
models as of the last generated file. Each run compares the declared models
with that snapshot and writes only the difference to the next
`migrations/NNNN_<name>.sql`:

| Change | SQL |
| --- | --- |
| new model | `CREATE TABLE` + indexes + RLS |
| new field | `ADD COLUMN` (a new required field needs `porDefecto`, or it refuses) |
| `antes: "old"` | `RENAME COLUMN` |
| type or `max` | `ALTER COLUMN … TYPE … USING` |
| `requerido` | `SET` / `DROP NOT NULL` (fills NULLs with the default first) |
| `porDefecto` | `SET` / `DROP DEFAULT` |
| enum values, `min`, `max` | the named CHECK is dropped and re-added |
| `unico`, `indice` | `ADD` / `DROP CONSTRAINT`, `CREATE` / `DROP INDEX` |
| `acceso` | the four RLS policies are recreated |
| removed field or model | **destructive**: written as a comment unless `--allow-destructive` (a removed required column loses `NOT NULL` so inserts keep working) |

It **never runs SQL**. It does not read `DATABASE_URL`. Review the file, then
apply it with the usual runner (`bun run scripts/migrate.ts`, or enabling the
kon from the panel with a DDL connection), which also applies
`funciones-de-agente.sql` first. Commit the snapshot with the migration.

The models are TypeScript, so the command loads them with `bun` (a one-off
script written into the model's folder and deleted afterwards) and computes the
diff with `@kitsuden/shared`. You need `bun` on the `PATH` and a built
`@kitsuden/shared` (`pnpm --filter @kitsuden/shared build`). The previous
generator (drizzle-kit export of a kon's whole `schema.ts`) is still there
behind `--drizzle`.

### Day 2: changing a model that already has rows

Checked against real rows in `tests/unit/modelos-dia-2.test.ts` (2026-10-28).
The runner applies each file in **one transaction**, so a migration that fails
on your data leaves nothing half done.

| You want to | What happens | Do this |
| --- | --- | --- |
| Add a required field | Refused without `porDefecto` (it would fail on existing rows) | Give it `porDefecto`, or add it optional, fill it, then make it required |
| Add a required field with `porDefecto` | Existing rows get the default | Nothing else |
| Make an optional field required, with `porDefecto` | The migration fills the `NULL`s with it, then `SET NOT NULL` | Nothing else |
| Make an optional field required, **without** `porDefecto` | Warning `fill them first`; applying it fails if any row is `NULL` | Write a data migration first (`UPDATE … SET x = … WHERE x IS NULL`), apply it, then generate the change |
| Make a field `unico` | Fails if there are duplicates | Clean the duplicates first |
| Narrow enum values, `min` or `max` | Fails if rows violate the new CHECK; the old CHECK stays | Update those rows first |
| Rename a field | `antes: "old"` keeps the data | Never delete and re-add |

The safe order for anything that touches existing data is always the same:
**add (optional) → fill → constrain**, one migration each.

## Deploy order

1. Declare or change the model; `kitsuden makemigrations`; review the SQL.
2. Apply the migration with the migration runner (DDL connection).
3. Deploy the API with the kon (its routes are generated at start-up).
4. Enable the kon (`modules.enabled`) if it is new.
5. Grant agents the scopes they need (`<model>:read`, `<model>:write`).

## Traps

- zod 4: defaults live in the column, not in zod, because `.default()` after a
  `.transform()` skips the transform. Dates use `esquemaFecha()`; uuids use
  `z.guid()`; records take two arguments.
- A model name is its scope: it cannot repeat across kons (`defineKonDeModelos`
  throws) and cannot be a core scope prefix (`admin`, `mcp`, `kon`,
  `datasets`…).
- Renaming a model's `tabla` renames the table and recreates its policies;
  renaming the model itself (`nombre`) is a new model plus a removed one.
- Owner rows created by the system have `owner_id` NULL: only the system and
  admins see them.
